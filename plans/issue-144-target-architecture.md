## 0. Owner refinement: decentralized primary information (Hdez), one current contract, rebuildable engine

**2026-11-24 — revised preferred direction, for discussion; no implementation authorization.** The owner challenges the previous assumption that ContextCanon must maintain a parallel library of all historical publications. This changes the research priority from optimizing many snapshots to eliminating the requirement to keep them in the live working tree. The owner confirms **no onboarding runs are currently active**. The following direction supersedes the initial staged dual-reader/dual-runtime and permanent live-history assumptions in sections 2–8 where they conflict. Previous sections remain evidence and compatibility requirements, not a mandate to retain the old implementation.

### Minimal durable truth

Maintain decentralized primary information (Hdez, Hauptinformationen dezentral) at the relevant Node/folder scope. Hdez is the logical authority, not a decided file extension, grammar, number of files, schema or database. It holds local authored meaning, explicitly important relationships, the currently valid accepted contract, sparse human decisions, and current State/Plan where there is actual work. Ordinary files need no management record. Actual project documents remain authoritative at their normal locations; Hdez references them. Stable identities are independent of path and preserved on conversion.

Each managed consumer needs at most **one current valid contract per relationship or one aggregate contract with one exact binding per source**, not a sequence of accepted historical contracts. A consumer with multiple Parents necessarily keeps multiple bindings, which may refer to shared exact content. Keep enough original accepted source content/closure to reconstruct the effective accepted context and compute meaningful diffs even when the provider changes or disappears. A hash alone detects change but cannot reproduce old content. Reuse identical baseline bytes when useful; do not mandate content-addressed infrastructure before a small real test. File dependencies can use a hash only if the exact baseline is otherwise accessible or only change detection is intended. Different consumers may accept different source revisions; preserve all currently necessary ones, not just the provider's latest. This is a live reachability constraint, not a general history ledger.

Git is the historical versioning system. Historical accepted v4 packages must remain exactly reconstructable via retained original bytes in reachable commits/tags or verified portable archival return copies (including external package closure, exact manifest/member bytes and EOL evidence). Verify historical recovery before retiring live copies; never assume uncommitted, ignored, missing or unreachable bytes are in Git. No Git-history rewrite, automatic pruning or silent loss. New contracts need not use v4 internal representation; preserve old identity and standalone legacy export through a separate offline verification/export path, not a second production engine. If exact reproduction is impossible, refuse or explicitly retain the relevant legacy bytes. A baseline tag/backup is a proposed migration gate, not already created.

The signed-contract metaphor is semantic, not a requirement for cryptographic signatures. Distinguish offered revision, governing accepted baseline and implementation/verification evidence. Prefer one final complete acceptance+validation operation replacing the current contract once required checks/decisions are satisfied; a pending candidate is work, not another accepted history snapshot. If #121 permits acceptance before implementation/verification, the accepted normative binding and last verified evidence must remain distinguishable (and any still-needed exact verification baseline retained). Do not label work complete or silently weaken governance to enforce a one-copy slogan. Whether mandatory acceptance must wait for implementation/validation is an explicit remaining owner decision. Declined/deferred candidates and unresolved work do not replace valid contracts. Candidate observations can be refreshed or discarded; decisions remain tied to exact revisions, and cannot silently carry over to a changed candidate.

### Rebuildable engine and user views

New engine starts with Hdez + user-owned files + verified accepted contract material (and optionally explicitly fetched discovery candidates). Deterministically discover scopes, load, validate, resolve relationships, construct in-memory model, compile effective Context, compare current known source vs contract, and generate projections. No persistent authoritative engine DB, hidden state or incremental cache is required; any index/cache is disposable. On checkout or restart the same inputs produce the same effective result. Offline unknown candidate is not current. Missing/corrupt contracts fail closed. No LLM needed for enumeration, comparison, compilation or projection; semantic decisions and adaptations may be proposed by a human/LLM. Preserve the current product semantics and reuse existing tested code where it fits, without forcing the new engine through legacy Markdown/storage APIs.

Generate three views from the same model: compact accepted CONTEXT.md and required usable resources (harness-independent), a readable HTML5 cockpit showing current/pending changes, affected artifacts, next actions and State/Plan, and structured JSON for LLM work (exact source and baseline identities, changed IDs/content or links, impact, decisions required, validation/evidence, constraints, relevant Plan). The pending diagnostic view does not change the accepted publication identity. JSON is a scoped task input, not permission to perform or approve changes. HTML initially can be a static report, offline and readable without server; interactive actions require a deliberately authorized write path to Hdez (e.g. small local command/localhost adapter), not uncontrolled browser filesystem writes. A click requests a validated operation with expected old identity, refuses stale state, preserves human fields, updates only the proper Hdez/contract, then regenerates. No browser-side second authority, general web app, automatic accept, or always-running service required. Compare static HTML plus explicit command before investing in interactivity.

### Close the loop: Hdez authoring and write interface (owner refinement)

Hdez is not merely an input format for a read-only compiler. The initial vertical proof must include the reverse path from human or LLM decisions to the same decentralized primary information. A human can edit the Hdez file directly; a small programmatic interface can perform equivalent targeted edits for humans, LLMs, onboarding, and eventually HTML controls. Git versions the actual Hdez files. No separate authoritative database, event log, decision queue, or synchronization between two masters. A file watcher is optional convenience, not a requirement; explicit reload/build is sufficient initially.

Keep the processing engine and authoring operations conceptually distinct, but they may be in the same Python package/CLI. The engine rereads and validates the current Hdez on invocation regardless of which editor wrote it. The authoring interface loads current Hdez, validates the intended change and its scope, updates only the owning Hdez/necessary contract material without losing unrelated content, and makes the next engine rebuild possible. Prefer a small command/JSON interface first, not a server or special LLM protocol. Direct human editing remains a first-class route and is validated on the next load; no mandatory UI or API for ordinary authoring.

Minimum round-trip examples: add/edit a local rule; record acceptance/rejection/deferral of a specific offered rule/revision; record an implementation or validation result with the relevant exact revision, outcome and evidence reference; update Plan/State; finalize and replace a contract when applicable governance permits. These are examples of semantic operations, not a decided command syntax/schema. A local new rule and acceptance of an inherited change are different operations. A positive validation result is not automatically a valid contract; an LLM report is not automatically authorized approval. Authorized actors and required evidence are decided by the existing governance/owner policy, not the transport.

For programmatic updates, check expected source/candidate identity before writing, reject stale edits and preserve unrelated manual changes. Repeated identical operations should not multiply records or generate unnecessary changes. Use safe file replacement and, only where multiple files truly must change together, a recoverable publication boundary; keep the implementation proportionate. Manual edits cannot be assumed authorized just because they parse: enforce invariants on reload, report broken references/inconsistent contracts, and do not silently accept latest or treat an unverified assertion as proof. Git review and filesystem permissions remain important; direct editing is not a security boundary.

The first disposable prototype must demonstrate both paths: manually add a rule to Hdez, rebuild; then use the programmatic interface to record a changed Parent's review decision, actual validation evidence and a contract replacement, rebuild again. Show the result in CONTEXT.md, HTML and JSON as appropriate, inspect Git diff (only necessary authored/contract changes and deliberately tracked projections), and rebuild with all derived state removed. Demonstrate rejection of a stale programmatic decision after an intervening manual edit, and restore a committed Hdez/contract state via Git. Do not require HTML interaction, automatic file watching, or a production API to prove the architecture. Onboarding and later HTML controls reuse the same write semantics rather than inventing independent persistence.

## 0A. Owner-approved internal separation and staged transition (2026-11-28)

**Decision:** owner approves the internal architectural separation below; record it now. This is an architecture decision, not authorization to implement, migrate a real project, delete legacy code, publish confidential inputs, or merge. ### Boundaries and responsibilities

- **Snapshot Engine:** independently usable immutable byte/object identity, integrity, storage, resolution, publication, retrieval, replication and local retention/release. Same logical operations at Node, filesystem/repository/workspace, intermediate and remote scopes; Git/GitHub may be adapters, not a mandatory central service. Separate discovery locator, logical publication/revision, exact content identity, and physical availability. Prefer one physical copy within a chosen autonomy/access boundary, intentionally replicate across independently portable boundaries. A Node needs direct logical access, not a separate physical store. Accepted dependencies must remain locally resolvable within their declared autonomy boundary even if an upstream disappears. No assumption of global knowledge of consumers; local unreferenced does not mean globally unused. No automatic destructive GC or distributed consensus. The store transports opaque report objects but does not decide acceptance, compliance or exceptions.
- **Dependency Core:** small deterministic, independently usable library for element identity, directed typed relations, observations, exact confirmed checkpoints, comparison and potential impact. Distinguish stale/unknown/invalid; no semantic assertion of correctness, mandatory full graph, persistent authoritative graph DB, or universal workflow engine. No ContextCanon-specific types/imports. A dependency checkpoint can include both source and dependent revision/evidence where needed. Reuse only proven common behavior.
- **ContextCanon:** domain-specific Hdez, normative Parent/Reference distinction, Rules/Topics/Resources, provenance and interpretations, composition, export boundary, acceptance policy, authority for exceptions, verification obligations, authoring, onboarding and generated Context. A Reference is not inherited governance; transport and discovery do not imply acceptance. Preserve offline effective accepted Context and stable identities. Current override implementation records provenance/reason, but compiler _apply_rule_changes does not itself prove upstream authorization; do not claim that enforcement already exists. Authority and explicit exception approval must be verified in the new design. Optional explicit scope-limited reports upstream distinguish observed/reported/verified/unknown, with no default private data disclosure.
- **Artifact Tracker:** optional domain module/client of the same core/protocol for selected file/document/section dependencies, variants, implementation/test/documentation consistency and actionable impact; not mandatory for ContextCanon users. Use ordinary file locations; no automatic all-file modeling or per-file contract bureaucracy. Test without Context compiler.
- **Change management:** new open research boundary, see section 0B. Detecting impact is not managing its resolution. Do not finalize a process architecture or implement a separate workflow product until research and vertical tests demonstrate a minimal useful design.

Start in one repository/installable product, clear internal packages and dependency direction, with no reverse imports from generic layers into ContextCanon. Reuse existing tested algorithms where appropriate. Existing version_store/candidate_store/git_transport/package/sources mix transport, Context package semantics and acceptance: split responsibilities, not just move files. Use dependency/interface contract tests before any later repository split. Do not standardize a network protocol or spin out new services/projects prematurely. Snapshot infrastructure may later be independently released; a global store is not a prerequisite.

Prefer YAML Hdez with optional separate sealed immutable object material (variant B as owner-preferred candidate, not committed format). Binary/compressed objects and expected digest reduce accidental Find/Replace damage; Git binary attributes and exclusion are defense in depth, not cryptographic approval. Generated HTML/PDF/JSON views are not authority. Keep immutable originals (e.g. chat, meeting notes, policy) distinct from editable, independently revisable interpretations and explicit promotion to effective Context (#143); no forced propagation of raw private originals or their sensitive metadata. Full chat importer remains deferred; use an existing nonconfidential fixture for the shared object proof. Final encoding, layout, retention policy and names remain open.

This is in addition to, not instead of, effective CONTEXT.md parity. The regenerated CONTEXT.src.md is a read-only compatibility/review/export projection, not a second editable source; Hdez is sole authority after cutover. ## 0B. Research gate: engineering change management (open, not an approved component design)

The owner identifies the unresolved product risk: reliable distribution and fine-grained dependency detection can amplify work into unmanageable cascades; a human or LLM cannot simply be told to handle every dirty flag. Distribution, impact detection, normative applicability and execution/closure are distinct. Before broad artifact dependency adoption, prove that identified changes can be grouped, prioritized, performed and verified without disproportionate administration.

### External precedents (initial desk research, not a certification claim)

- [NASA Systems Engineering Handbook 6.5 Configuration Management](https://www.nasa.gov/reference/6-5-configuration-management/), [6.2 Requirements Management](https://www.nasa.gov/reference/6-2-requirements-management/), [SWE-080 Track and Evaluate Changes](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695459/SWE-080%2B-%2BTrack%2Band%2BEvaluate%2BChanges): controlled proposal, impact assessment, decision, implementation, verification and closure; bidirectional traceability of requirements/design/test. Borrow the lifecycle, not NASA's organizational bureaucracy.
- [FAA Airworthiness Directives](https://www.faa.gov/aircraft/air_cert/continued_operation/ad), [14 CFR 39.19](https://www.govinfo.gov/content/pkg/CFR-2025-title14-vol1/xhtml/CFR-2025-title14-vol1-sec39-19.html), [14 CFR 91.417](https://www.law.cornell.edu/cfr/text/14/91.417): applicability to actual configuration, current compliance records with revision and method, authorized alternatives. Last locally accepted is not necessarily currently externally compliant; mandatory effective dates/deadlines may matter. No aviation certification implied.
- [IBM DOORS Next link validity](https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/doors-next/7.1.0?topic=projects-link-validity), [impact analysis](https://www.ibm.com/docs/en/engineering-lifecycle-management-suite/doors-next/7.1.0?topic=requirements-analyzing-impact-change): suspect links require review, not automatic invalidation of artifacts; work items can link to requirements.
- [NIST SP 800-171 Rev 3](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/800-171r3/NIST.SP.800-171r3.html): controlled changes and security impact analysis. Proportionate policy rather than identical controls on every change.
- [Concepts of change propagation analysis in engineering design (2022)](https://doi.org/10.1007/s00163-022-00395-y): engineering change propagation / Design Structure Matrix approaches; prediction is not proof of actual downstream change.

### Candidate minimal process to investigate (not a committed workflow/schema)

Use an explicit **change case/work package** as the unit of work rather than one ticket per changed edge. Derive findings from exact accepted/current revisions. Group repeated root changes and related findings by compatible scope, responsibility and target revisions; preserve distinct consumer obligations and evidence. A finding is not an action. Applicability/impact assessment decides no action (with reason where necessary), action required, authorized alternative/exception, defer/open or unknown. A work package may reference an existing Issue and PLAN rather than duplicate it. Persist only decisions, ownership, actual plan, exact evidence and necessary checkpoints; derive summaries, dirty flags and candidate lists. No forced per-link approvals for benign guidance; #121 policy remains explicit and unresolved.

Freeze exact input revisions and affected obligation set for review/execution; LLM receives scoped diff, relevant sources, rules, affected artifacts, constraints and requested verification. Human/LLM proposes adaptations; real checks or authorized human assessment provide evidence. Bind evidence to relevant source AND dependent revisions/test context; later edits invalidate only relevant evidence. Recompute impact after each bounded work block: new actual changes can expose new obligations, merge duplicates and stop at unchanged effective outputs where justified. Distinguish potential transitive impact from actual change; graph coverage is partial, so closure proves only modeled/assessed scope, not universal compliance. Require explicit disposition of every in-scope required finding and valid evidence/authorized exceptions before completion; deferred or unknown required work cannot silently close. If new provider revisions arrive, preserve frozen case or rebase with explicit review; never silently reuse stale approvals. No globally atomic rollout; independently valid checkpoints per autonomy boundary with truthful partial status. Separate acceptance of obligation, implementation and verification; atomic final baseline only if policy permits. Use existing Git/Issue/PLAN/STATE workflow as first executor, not automatic LLM orchestrator/scheduler. Research whether the reusable part is a pure reconciliation function, optional change module, or application policy; no premature engine or general BPM system.

**Success test:** one root change across a diamond or several children plus a changed local spec; shared diff once, grouped work, no lost distinct required decisions, no task for irrelevant changes, actual adaptation/validation, stop/no-action branch, later input edit invalidates relevant result, resume after interruption, close only when all modeled required obligations accounted for. Compare number of prompts/tasks/files and evidence quality to legacy replay. Test incomplete graph, inaccessible source, invalid/expired approval, and ongoing change; no claim of automatic total impact discovery or certification. Only then decide whether expanded artifact tracking has net value.

## 2. Recommendation and boundaries

Choose a shared model/engine with existing compiler boundary (option B), leaving physical storage independently replaceable (option C as a later measured choice). A Node remains the outer frame, not a generic knowledge item with no behavior. A compiler remains the authority for composition, not the graph traversal engine.

Four useful primitives, not four mandatory ledgers:

1. Element: stable domain identity if explicitly managed, type, owned location and revision evidence. Existing Node, Rule, Topic, Resource IDs remain; managed artifact identity may be allocated on first meaningful relation/annotation. Ordinary discovered paths need no UUID, record or version number. A folder inventory entry is not a semantic Node. A Resource can point to an artifact without conflating Topic Resource identity with physical file identity.
2. Relation: dependent -> source, with typed effect and rationale when useful. Reuse relationship lookup/diff/checkpoint mechanics, not behavior. Parent/Reference composition, Topic navigation, containment and artifact dependency are distinct; only explicit important dependency edges enter impact review. Keep selected variant as an explicit optional choice, not a general variant lifecycle system. No guessed causal links.
3. Checkpoint: exact source revision the relation last accepted/reviewed, plus dependent revision and evidence where verification is claimed. Full Node binding includes Node ID, version, normalized/package digest and schema; location/discovery is not identity. File evidence normally exact byte hash; selected folder membership/content scope must be explicit if folder revisions are used. No per-file SemVer. Latest-known observation is separate, with freshness/unknown/deleted/corrupt distinction.
4. Assessment/work: sparse authored decision against specific old/new identities (no action, needs change, deferred/refused, verified, justified exception), optional link to ordinary Plan/State/evidence. No per-edge mandatory plan. Derived review-needed status computed from checkpoints, source observations and applicable policy. Verification must bind both relevant input and actual output revision/evidence. A review can find no change necessary; advance that checkpoint explicitly without pretending work occurred.

Engine operations conceptually: enumerate relations; resolve exact baseline and separately observe candidates; compare; report impact; validate a scoped decision; commit the appropriate checkpoint only on explicit authorized operation. No LLM needed for inventory/diff/status; an LLM can propose decisions, not establish verified truth. Do not introduce a generic workflow DSL, event sourcing, scheduler, full project graph, per-section tracking, automatic rewriting, database server or required GUI. Reuse existing domain-specific validators; one or two concrete consumers must demonstrate net code and UX simplification before extracting a common abstraction.

| Relation | Source change | Effect | Baseline advancement |
| --- | --- | --- | --- |
| Parent | changed normative export | candidate and structural conflict/diff; effective Child retains accepted Parent | reviewed exact package acceptance, then publish Child; descendants see only changed Child export |
| Reference | changed package | direct informational update candidate, no inherited governance | explicit pin update under existing policy; later low-friction policy requires owner approval |
| Artifact depends on spec | changed source hash | potentially stale, not automatically invalid; no composition | no-action review or completed/verified adaptation against exact revisions |
| Containment / navigation | path/member changes | regenerate navigation only | no governance checkpoint unless explicit scoped dependency |
| Optional selected example | alternate selected explicitly | current navigation identifies authority, other variants stay available | explicit selection, no deletion or inferred supersession |

Parent graph remains acyclic; artifact graph need not be globally acyclic (mutual implementation/test dependencies are plausible). Direct impact first, transitive potential impact only as bounded deduplicated traversal with reason/path; do not fake changed output revisions. Structural cycles invalid where composition requires DAG, not a universal constraint. Multi-Parent diamond convergence remains a compiler concern. An update to a candidate or local status does not create a new accepted version. A real local authored Context change may legitimately create one.

### Governance

Kp (producer intent) and Kc (consumer handling) are discussion vocabulary, not a finalized schema. Proposed minimum intent distinctions: binding requirement, recommendation, information. Reusable module is a role, potentially containing any of these; Required/Optional Topic loading is independent. Applicability, review policy, implementation and verification must not collapse into one enum. Default all imported legacy normative material to existing strict semantics, not relaxed guidance; reclassify deliberately. Review/accept still works for whole exact package at first; lower-friction or bulk decisions require explicitly defined scope, conflict checks, evidence of equivalent relevant changes and traceable per-consumer outcomes. Do not infer authorization from a small diff or SemVer. No-action acceptance and no-action artifact review are different acts. New critical requirement can be accepted but not implemented, or already implemented before acceptance. Exception must be justified and version-scoped; changed rule cannot inherit stale verification silently. Non-normative Reference is not a weak Parent.

## 3. Authority, compiler and storage boundaries

- **Authored truth:** Node local meaning, relationships/locators, sparse artifact descriptions/edges, explicit decisions, overrides and authored work plans. One writable authority per fact. Human-facing editor may join these facts in one view; it does not require one file. Preserve project-owned original files.
- **Accepted truth:** immutable exact baseline and explicit consumer binding; producer publication and consumer acceptance independent. Changes to discovery URL/ref alone must not advance accepted identity. Store sparse per-rule handling/evidence separately from derived candidates; only accepted normative content/actual authored Context changes affect publication identity under the applicable contract.
- **Observation/derived truth:** current filesystem inventory, known candidate, diffs, potential impacts, project map, local cockpit. Rebuildable, no implicit acceptance, no write to authored meaning. Default check stays read-only; explicit refresh/preview can be evaluated. If a checked-in view becomes stale after checkout, mark/check input identity or regenerate; remote latest unknown offline.
- **Published truth:** preserve existing entry and usable package for arbitrary harnesses, without runtime or network; effective accepted Rules, direct informational References, provenance, Resource links, adapters and conditional navigation. Do not dynamically append status to sealed v4 CONTEXT.md: even local/non-inherited bytes can change exact package digest. Prefer adjacent derived view and a stable non-normative pointer for newly published nodes (one intentional compatibility change, not per-refresh). If pointer could be inherited or packaged, define export boundary explicitly; no self-reference. Root map #124 and inner inventory use the same projection inputs, not second sources of truth.
- **Storage:** API reads exact version by full binding, validates, compares, materializes standalone portable package. For first phase keep existing storage/renderer and v4 format. Later compare thin immutable refs to original manifest bytes, binary content objects/segments and compositional publication with explicit new package contract. Existing v4 manifests and all member bytes reconstruct exactly; new composition identity cannot pretend to be v4. Binary objects avoid routine text Find/Replace, but hashes only detect corruption; protect ownership and explicit read-only inspection. A single mutable Git-tracked binary DB is a poor default for parallel branches; local disposable index is acceptable if regenerated. No external mandatory service, no Git LFS dependency, no automatic GC. Preserve complete retained histories until an independently approved retention policy proves closure of all current publications, exact pins, review/onboarding/reset/migration roots and historical contracts across branches. Git history can only recover committed reachable bytes; ignored data needs filesystem backups. Never rely on provider latest or network to recover accepted data.

Inventory: reuse deterministic repository enumeration/path safety from onboarding, but separate ordinary navigation inventory from Evidence triage (which intentionally omits ordinary code by default). List scoped folders/files including code, tracked and nonignored untracked according to explicit policy; decide treatment of empty dirs and tracked ignored paths, submodules/nested repos, symlinks, case collisions, generated namespaces. Stop at nested Node boundary and link it, do not attribute its contents to enclosing Node. No generated/history/evidence tree in user inventory. Canonical portable relative paths and raw byte hashes when needed; no silent same-content rename inference. Explicit rename preserves managed ID; ambiguous/missing paths become unresolved; ordinary file changes do not bump Node packages. A compact top-level orientation and optional navigable detail beats dumping thousands of file names into prompts.

Authoring bake-off after model gate: (a) strict compact structured text (YAML possible), (b) prose + small typed metadata/binding surface, (c) CLI/TUI or lightweight cockpit editing same typed model. Compare one real create/edit/import/override/rename flow; count manually entered machine metadata, collisions, prompts, diffs, editing recovery. Reject duplicate authorities and hidden parser grammar; no chosen syntax/schema/UI yet. Keep direct human-readable export of authored meaning; editing generated CONTEXT is never authorized.

## 4. Migration and coexistence (three different workflows)

**Converter**: old authoring syntax -> typed authored data plus import binding information. Inputs: CONTEXT.src.md, machine-relevant config including discovery mappings, verified last publication where local legacy imports are unpinned, accepted versions and provenance. Parse supported legacy forms with current parser/normalizer under controlled read-only staging; preserve Node/Rule/Topic/Resource and onboarding placement IDs, grouping/order, text, Required/Optional, why, Overview/State/Plan, adapter flags, overrides/removes, origin and transport, explicit and legacy Parent/Reference semantics. Preserve comments/unknown prose losslessly as raw original or explicit retained text; if an unknown machine-significant field, conflict or missing identity cannot be mapped, stop with file/line/next action. Do not allocate existing IDs again. Legacy local unpinned baseline comes from verified prior Child publication, not live Parent; unresolved baseline refuses. Converter does not publish, fetch, accept or migrate history. For genuinely new entries without assigned identity use a separately reviewed allocation, not silent migration.

**Importer**: existing managed project -> new model/ownership store. Discover root and nested Nodes, authoring plus config, all accepted Parent/Reference binding tuples including transitive imports, manifests, retained v0–v4 packages, Resource origins/exact bytes/closure, current publications, historical versions, pending reviews/candidates, accepted inventory and onboarding decisions/journal/handoff state. Audit ownership, version formats, duplicate IDs, stale or broken states, paths and exact packages. Preserve stale reviews as stale, refusal/defer/pending status; do not upgrade to provider latest. Generate a read-only report with per-node equivalence, unknowns and planned writes. Stage copy into separate namespace/worktree; compile from new model against frozen same packages with legacy renderer; compare canonical authored meaning, accepted tuples, exact old package bytes/digests, effective Rules/Topics/Resource bytes and links, provenance, export and check behavior. Require zero unexplained drift. If an intentional new rendering is later approved, assign a new publication explicitly; never mutate old identity. Verify all retained v4 exports byte-for-byte (including manifest). Preserve legacy v0–v3 readable history; do not claim recovery of never-retained bytes. Use original hash/size validation for any Git EOL recovery, not global normalization.
 
**Onboarding**: discovery and semantic decisions for not-yet-managed project/subtree. It is not a converter/importer. Existing project import requires no LLM/no repeat of prior acceptance. A mixed or partly onboarded project can import verified existing Nodes and use original onboarding for missing scope only, without pretending arbitrary incremental semantic re-onboarding exists today.

**Active onboarding runs**: preserve by default under matching old runtime/format until completed/reset or separately migrated. Do not switch their authoring format while journal or review hashes bind old paths/bytes. Where active migration is required, reuse existing onboarding migration pattern; retain exact Evidence/review/RESULT/ZIP bytes and accepted Catalog/enclosing package bindings, translate only schema-owned physical routing/PLAN blocks; preserve stale status, original hashes and rollback. If equivalence of review or journal cannot be proved, keep legacy engine for that run rather than reaccepting or dropping it. Fresh clone can reconstruct accepted inventory but not ignored uncommitted Evidence/workspaces; full filesystem return copy required. Preserve custom workspaces, scoped run ownership, historical runs, ignored IDE metadata not explicitly bound. Recovery refuses unknown files, symlinks, corruption and changed after-images.

Transition: dual legacy/new *readers* into model with exactly one authority per Node and explicit format selection; no silent priority when both editable formats exist. Legacy source remains read/write via old tool until owner activates new format. Shadow converter/importer operates read-only or isolated, no dual-write synchronization. Activation only after complete staged verification; retain legacy files in return copy/immutable original, record activation, backup plus Git checkpoint, atomic small state switch where possible and resumable journal with hash-bound writes/retirement. Recovery before activation leaves old authoritative; after activation resume or explicit rollback against verified recorded bytes (never overwrite later human edits). Retire old format only after independently approved proven recovery. Old branches retain old format and pinned tool version; new tool reads both; mixed-format merges require explicit reconciliation of identity, binding and authority, not last writer wins. Test two branches changing different relations, divergent same pin, stale receipts, branch switch and path/EOL differences. Cross-repo acceptance closure self-contained on offline consumer clone. Remote discovery optional, local paths portable or explicitly unresolved, no path alias pretending to be identity.

Existing versions migrate and onboard migrate are useful precedents, not a full new importer. No project migration until owner approval.
