## 1. Findings from current implementation

The original folder-to-Official-Context contract works. Keep it, including progressive disclosure, stable IDs, local Overview/State/Plan, Rules, Topics, Required/Optional Resources, explicit Parent and Reference, unordered multi-Parent composition, explicit Overrides/Removes, provenance and offline portability. Nested directories are not implicit semantic ancestry.

- [model.py](../src/contextcanon/model.py) already has typed ParsedNode, SourceRef, ParentRef, Rule, Topic, CompiledPackage and CompiledNode. The compiler is not a Markdown concatenator. [compiler.py](../src/contextcanon/compiler.py) parses first, resolves exact accepted packages, composes only normative Parent material, applies changes, checks conflicts/identity/cycles and collects Resources. [package.py](../src/contextcanon/package.py) separately verifies semantic and exact byte identity, and supports v0–v4 readers. Retain these domain types and algorithms rather than replacing them with generic dictionaries or a graph database. The existing compiler accepts staged source/file/package overrides, a particularly useful seam for a typed input.
- [source format](../docs/context-source-format.md): build already stages mechanical authoring migrations and allocates missing IDs; check is read-only. Location discovery is split across authoring and configuration. #123's Markdown-specific solution is reopened, not its identity/location separation.
- [maintenance](../docs/maintenance.md): direct References are pinned but non-normative/local; package-only changes with unchanged normative export do not require propagation. This existing export distinction is valuable. #140 resolves local unpinned dependencies using previously verified published bindings, not latest live bytes. Preserve that repair.
- [version library](../docs/node-versions.md) and [storage_migration.py](../src/contextcanon/storage_migration.py): shared Git-root library, short tokens as locators only, exact package keys and explicit preview/apply relocation, verify before narrow retirement, resumable receipts. Do not replace this with an unbounded nested store.
- [onboarding placement](../src/contextcanon/onboarding_placement_publish.py) has explicit structured review items, but serializes them to managed Markdown sections, reparses via Compiler(source_overrides, file_overrides, package_overrides) in preview, then writes, recompiles, verifies pins, and records acceptance. _render_node_source, _replace_managed_section, _render_parent_body, format_source are format-specific seams, not reasons to rewrite the review process.
- [skeleton materialization](../src/contextcanon/onboarding_structure_materialize.py) recovers provable existing identity and checks owned output paths, creates only missing skeletons; [reset](../src/contextcanon/onboarding_reset.py) journals managed before/after bytes and verifies reversal, with resumable reset. [onboarding_migration.py](../src/contextcanon/onboarding_migration.py) verifies inputs/ownership, exact packages, handoff/ZIP and review bindings, copies before activation/retirement. Preserve these carefully acquired safeguards.
- Draft #142's actual paired #137 experiment: v4 82 changed paths / 9,198 added lines / 808 checkout paths / 9,183,552 checkout bytes; CAS 44 / 3,814 / 509 / 5,987,138; tar 32 / 529 / 391 / 9,711,851; tar.gz 32 / 529 / 391 / 5,755,577. The #121 report of 128 changed files/eight approvals is distinct evidence. Do not generalize synthetic eight-edge results.

Review scope: static implementation inspection, docs, test inventory and reported historical CI/prototype results; no new runtime/CI executed. PLAN/STATE pre-merge language is stale on accepted main; record actual baseline without reopening or closing unrelated issues here.

## 2. Recommendation and boundaries

Choose a shared model/engine with existing compiler boundary (option B), leaving physical storage independently replaceable (option C as a later measured choice). A Node remains the outer frame, not a generic knowledge item with no behavior. A compiler remains the authority for composition, not the graph traversal engine.

Four useful primitives, not four mandatory ledgers:

1. Element: stable domain identity if explicitly managed, type, owned location and revision evidence. Existing Node, Rule, Topic, Resource IDs remain; managed artifact identity may be allocated on first meaningful relation/annotation. Ordinary discovered paths need no UUID, record or version number. A folder inventory entry is not a semantic Node. A Resource can point to an artifact without conflating Topic Resource identity with physical file identity.
2. Relation: dependent -> source, with typed effect and rationale when useful. Reuse relationship lookup/diff/checkpoint mechanics, not behavior. Parent/Reference composition, Topic navigation, containment and artifact dependency are distinct; only explicit important dependency edges enter impact review. Keep selected variant as an explicit optional choice, not a general variant lifecycle system. No guessed causal links.
3. Checkpoint: exact source revision the relation last accepted/reviewed, plus dependent revision and evidence where verification is claimed. Full Node binding includes Node ID, version, normalized/package digest and schema; location/discovery is not identity. File evidence normally exact byte hash; selected folder membership/content scope must be explicit if folder revisions are used. No per-file SemVer. Latest-known observation is separate, with freshness/unknown/deleted/corrupt distinction.
4. Assessment/work: sparse authored decision against specific old/new identities (no action, needs change, deferred/refused, verified, justified exception), optional link to ordinary Plan/State/evidence. No per-edge mandatory plan. Derived review-needed status computed from checkpoints, source observations and applicable policy. Verification must bind both relevant input and actual output revision/evidence. A review can find no change necessary; advance that checkpoint explicitly without pretending work occurred.

Engine operations conceptually: enumerate relations; resolve exact baseline and separately observe candidates; compare; report impact; validate a scoped decision; commit the appropriate checkpoint only on explicit authorized operation. No LLM needed for inventory/diff/status; an LLM can propose decisions, not establish verified truth. Do not introduce a generic workflow DSL, event sourcing, scheduler, full project graph, per-section tracking, automatic rewriting, database server or required GUI. Reuse existing domain-specific validators; one or two concrete consumers must demonstrate net code and UX simplification before extracting a common abstraction.

| Relation | Source change | Effect | Baseline advancement |
| --- | --- | --- | --- |
| Parent | changed normative export | candidate and structural conflict/diff; effective Child retains accepted Parent | reviewed exact package acceptance, then publish Child; descendants see only changed Child export |
| Reference | changed package | direct informational update candidate, no inherited governance | explicit pin update under existing policy; later low-friction policy requires owner approval |
| Artifact depends on spec | changed source hash | potentially stale, not automatically invalid; no composition | no-action review or completed/verified adaptation against exact revisions |
| Containment / navigation | path/member changes | regenerate navigation only | no governance checkpoint unless explicit scoped dependency |
| Optional selected example | alternate selected explicitly | current navigation identifies authority, other variants stay available | explicit selection, no deletion or inferred supersession |

Parent graph remains acyclic; artifact graph need not be globally acyclic (mutual implementation/test dependencies are plausible). Direct impact first, transitive potential impact only as bounded deduplicated traversal with reason/path; do not fake changed output revisions. Structural cycles invalid where composition requires DAG, not a universal constraint. Multi-Parent diamond convergence remains a compiler concern. An update to a candidate or local status does not create a new accepted version. A real local authored Context change may legitimately create one.

### Governance

Kp (producer intent) and Kc (consumer handling) are discussion vocabulary, not a finalized schema. Proposed minimum intent distinctions: binding requirement, recommendation, information. Reusable module is a role, potentially containing any of these; Required/Optional Topic loading is independent. Applicability, review policy, implementation and verification must not collapse into one enum. Default all imported legacy normative material to existing strict semantics, not relaxed guidance; reclassify deliberately. Review/accept still works for whole exact package at first; lower-friction or bulk decisions require explicitly defined scope, conflict checks, evidence of equivalent relevant changes and traceable per-consumer outcomes. Do not infer authorization from a small diff or SemVer. No-action acceptance and no-action artifact review are different acts. New critical requirement can be accepted but not implemented, or already implemented before acceptance. Exception must be justified and version-scoped; changed rule cannot inherit stale verification silently. Non-normative Reference is not a weak Parent.

## 3. Authority, compiler and storage boundaries

- **Authored truth:** Node local meaning, relationships/locators, sparse artifact descriptions/edges, explicit decisions, overrides and authored work plans. One writable authority per fact. Human-facing editor may join these facts in one view; it does not require one file. Preserve project-owned original files.
- **Accepted truth:** immutable exact baseline and explicit consumer binding; producer publication and consumer acceptance independent. Changes to discovery URL/ref alone must not advance accepted identity. Store sparse per-rule handling/evidence separately from derived candidates; only accepted normative content/actual authored Context changes affect publication identity under the applicable contract.
- **Observation/derived truth:** current filesystem inventory, known candidate, diffs, potential impacts, project map, local cockpit. Rebuildable, no implicit acceptance, no write to authored meaning. Default check stays read-only; explicit refresh/preview can be evaluated. If a checked-in view becomes stale after checkout, mark/check input identity or regenerate; remote latest unknown offline.
- **Published truth:** preserve existing entry and usable package for arbitrary harnesses, without runtime or network; effective accepted Rules, direct informational References, provenance, Resource links, adapters and conditional navigation. Do not dynamically append status to sealed v4 CONTEXT.md: even local/non-inherited bytes can change exact package digest. Prefer adjacent derived view and a stable non-normative pointer for newly published nodes (one intentional compatibility change, not per-refresh). If pointer could be inherited or packaged, define export boundary explicitly; no self-reference. Root map #124 and inner inventory use the same projection inputs, not second sources of truth.
- **Storage:** API reads exact version by full binding, validates, compares, materializes standalone portable package. For first phase keep existing storage/renderer and v4 format. Later compare thin immutable refs to original manifest bytes, binary content objects/segments and compositional publication with explicit new package contract. Existing v4 manifests and all member bytes reconstruct exactly; new composition identity cannot pretend to be v4. Binary objects avoid routine text Find/Replace, but hashes only detect corruption; protect ownership and explicit read-only inspection. A single mutable Git-tracked binary DB is a poor default for parallel branches; local disposable index is acceptable if regenerated. No external mandatory service, no Git LFS dependency, no automatic GC. Preserve complete retained histories until an independently approved retention policy proves closure of all current publications, exact pins, review/onboarding/reset/migration roots and historical contracts across branches. Git history can only recover committed reachable bytes; ignored data needs filesystem backups. Never rely on provider latest or network to recover accepted data.

Inventory: reuse deterministic repository enumeration/path safety from onboarding, but separate ordinary navigation inventory from Evidence triage (which intentionally omits ordinary code by default). List scoped folders/files including code, tracked and nonignored untracked according to explicit policy; decide treatment of empty dirs and tracked ignored paths, submodules/nested repos, symlinks, case collisions, generated namespaces. Stop at nested Node boundary and link it, do not attribute its contents to enclosing Node. No generated/history/evidence tree in user inventory. Canonical portable relative paths and raw byte hashes when needed; no silent same-content rename inference. Explicit rename preserves managed ID; ambiguous/missing paths become unresolved; ordinary file changes do not bump Node packages. A compact top-level orientation and optional navigable detail beats dumping thousands of file names into prompts.

Authoring bake-off after model gate: (a) strict compact structured text (YAML possible), (b) prose + small typed metadata/binding surface, (c) CLI/TUI or lightweight cockpit editing same typed model. Compare one real create/edit/import/override/rename flow; count manually entered machine metadata, collisions, prompts, diffs, editing recovery. Reject duplicate authorities and hidden parser grammar; no chosen syntax/schema/UI yet. Keep direct human-readable export of authored meaning; editing generated CONTEXT is never authorized.

## 4. Migration and coexistence (three different workflows)

**Converter**: old authoring syntax -> typed authored data plus import binding information. Inputs: CONTEXT.src.md, machine-relevant config including discovery mappings, verified last publication where local legacy imports are unpinned, accepted versions and provenance. Parse supported legacy forms with current parser/normalizer under controlled read-only staging; preserve Node/Rule/Topic/Resource and onboarding placement IDs, grouping/order, text, Required/Optional, why, Overview/State/Plan, adapter flags, overrides/removes, origin and transport, explicit and legacy Parent/Reference semantics. Preserve comments/unknown prose losslessly as raw original or explicit retained text; if an unknown machine-significant field, conflict or missing identity cannot be mapped, stop with file/line/next action. Do not allocate existing IDs again. Legacy local unpinned baseline comes from verified prior Child publication, not live Parent; unresolved baseline refuses. Converter does not publish, fetch, accept or migrate history. For genuinely new entries without assigned identity use a separately reviewed allocation, not silent migration.

**Importer**: existing managed project -> new model/ownership store. Discover root and nested Nodes, authoring plus config, all accepted Parent/Reference binding tuples including transitive imports, manifests, retained v0–v4 packages, Resource origins/exact bytes/closure, current publications, historical versions, pending reviews/candidates, accepted inventory and onboarding decisions/journal/handoff state. Audit ownership, version formats, duplicate IDs, stale or broken states, paths and exact packages. Preserve stale reviews as stale, refusal/defer/pending status; do not upgrade to provider latest. Generate a read-only report with per-node equivalence, unknowns and planned writes. Stage copy into separate namespace/worktree; compile from new model against frozen same packages with legacy renderer; compare canonical authored meaning, accepted tuples, exact old package bytes/digests, effective Rules/Topics/Resource bytes and links, provenance, export and check behavior. Require zero unexplained drift. If an intentional new rendering is later approved, assign a new publication explicitly; never mutate old identity. Verify all retained v4 exports byte-for-byte (including manifest). Preserve legacy v0–v3 readable history; do not claim recovery of never-retained bytes. Use original hash/size validation for any Git EOL recovery, not global normalization.
 
**Onboarding**: discovery and semantic decisions for not-yet-managed project/subtree. It is not a converter/importer. Existing project import requires no LLM/no repeat of prior acceptance. A mixed or partly onboarded project can import verified existing Nodes and use original onboarding for missing scope only, without pretending arbitrary incremental semantic re-onboarding exists today.

**Active onboarding runs**: preserve by default under matching old runtime/format until completed/reset or separately migrated. Do not switch their authoring format while journal or review hashes bind old paths/bytes. Where active migration is required, reuse existing onboarding migration pattern; retain exact Evidence/review/RESULT/ZIP bytes and accepted Catalog/enclosing package bindings, translate only schema-owned physical routing/PLAN blocks; preserve stale status, original hashes and rollback. If equivalence of review or journal cannot be proved, keep legacy engine for that run rather than reaccepting or dropping it. Fresh clone can reconstruct accepted inventory but not ignored uncommitted Evidence/workspaces; full filesystem return copy required. Preserve custom workspaces, scoped run ownership, historical runs, ignored IDE metadata not explicitly bound. Recovery refuses unknown files, symlinks, corruption and changed after-images.

Transition: dual legacy/new *readers* into model with exactly one authority per Node and explicit format selection; no silent priority when both editable formats exist. Legacy source remains read/write via old tool until owner activates new format. Shadow converter/importer operates read-only or isolated, no dual-write synchronization. Activation only after complete staged verification; retain legacy files in return copy/immutable original, record activation, backup plus Git checkpoint, atomic small state switch where possible and resumable journal with hash-bound writes/retirement. Recovery before activation leaves old authoritative; after activation resume or explicit rollback against verified recorded bytes (never overwrite later human edits). Retire old format only after independently approved proven recovery. Old branches retain old format and pinned tool version; new tool reads both; mixed-format merges require explicit reconciliation of identity, binding and authority, not last writer wins. Test two branches changing different relations, divergent same pin, stale receipts, branch switch and path/EOL differences. Cross-repo acceptance closure self-contained on offline consumer clone. Remote discovery optional, local paths portable or explicitly unresolved, no path alias pretending to be identity.

Existing versions migrate and onboard migrate are useful precedents, not a full new importer. No project migration until owner approval.

## 6. Alternatives and risk

| Option | Advantages | Drawbacks / decision |
| --- | --- | --- |
| A: current architecture plus fixes | lowest immediate cost, established offline and onboarding | Markdown/authoring and repeated dependency mechanics remain; physical history issue independent; useful fallback and characterization baseline |
| B: typed model and shared change/checkpoint engine, same compiler contract | isolates authoring, shares change mechanics, deterministic and incremental, reuse review code | adapter/refactor cost, dual readers and transaction parity; recommended staged target |
| C: immutable compositional objects and generated views throughout | potential substantial reduction of materialized history/path noise and IDE contamination | new identity/export contract, readers, recovery, branch merge/retention and inspection complexity; test independently after B seam; no big bang |
 
Risk gates: a generic graph can erase semantics (typed operations and domain validators); auto classification can weaken security (strict legacy default and reviewed policy); status in sealed bytes causes cascades (separate identity/view); file hash proves change not failure (potential status only); accidental generated/history edit (ownership, binary experiment, digest checks, read-only views); binary branch conflict (immutable objects, small mergeable bindings, explicit same-relation conflict); EOL/case/long paths/symlink (raw bytes, canonical relative paths, root store, native Windows and Linux tests); converter omissions and stale acceptance (complete inventory, explicit refusal, parity proof); active runs and reset journal (legacy runtime isolation or exact reviewed relocation). Assess user time, commands, number of decisions, changes to effective identities, changed paths, diff lines/binary bytes, checkout and packed Git growth, read/compare/export latency and implementation complexity. Never call reduced file count reduced governance.
